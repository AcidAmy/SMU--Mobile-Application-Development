## 6.2 3~5 分钟深度技术汇报讲解提纲

### 第一部分：研究背景与立项痛点 (约 1 分钟)
- **痛点陈述**：大模型时代的数据资产“进不去”大模型。
  - Word 包含大量的 OpenXML 样式标签；
  - Excel 是多工作表的二维数据矩阵；
  - PDF 存在双栏排版、物理断行与表格塌缩难题。
- **目标**：打造一个高吞吐、低延迟、零幻觉、保留关键语义的统一预处理中枢。

### 第二部分：核心架构与创新机制 (约 2 分钟)
1. **统一门面与插件路由**：通过统一的 `convert()` 抽象接口，内部依据文件二进制指纹（Magic Bytes）精准分发给专用的转换器（如 `DocxConverter`、`PdfConverter`、`XlsxConverter`）。
2. **结构化语义映射**：
   - Word：映射 XML 标题为 Markdown 的 `#`，剥离多余字体大小与颜色；
   - Excel：智能识别多 Sheet 表格，按列生成标准 GFM 管道表格；
   - HTML：基于 BeautifulSoup 与 Markdownify 过滤脚本并保留语义超链接。
3. **安全性与特权防护**：引入 `defusedxml` 阻断 XML 实体攻击，提供 `convert_stream()` 杜绝路径穿越。

### 第三部分：系统演示与性能表现 (约 1 分钟)
- 现场运行 `./demo/quick_start.sh`；
- 向评委展示终端转换日志：4 个异构文件（PDF论文、Word正文、Excel财务表、HTML网页）在 **0.74 秒** 内全部完成转换，生成了清洗规范的 Markdown。

### 第四部分：总结与应用展望 (约 30 秒)
- MarkItDown 作为轻量无依赖的纯本地引擎，极大降低了文档处理的基础设施成本；
- 后续可无缝接入 LangChain、LlamaIndex 或企业级 RAG 向量数据库，作为知识入库的标准预处理前置节点。

## 6.3 答辩高频考点与标准解答（Q&A 秘籍）

### Q1：为什么统一转成 Markdown，而不是转成纯文本 (Plain Text) 或 JSON？
> **参考答案**：
> 1. 纯文本会丢失**多级标题层级（Heading）**和**二维表格结构**，导致大模型在 RAG 检索分块时无法感知文档层级，表格也会产生严重事实幻觉；
> 2. JSON 虽然结构化，但包含大量的花括号、引号和字段名样板代码，冗余的 Token 消耗巨大；
> 3. Markdown 是大语言模型预训练语料的原生格式，表达结构最简洁，**Token 压缩率与语义保留度综合表现最佳**。

### Q2：PDF 中的双栏排版与复杂表格，MarkItDown 是如何处理的？
> **参考答案**：
> MarkItDown 的底层采用了 `pdfminer.six` 和 `pdfplumber` 双引擎：
> 1. 利用 `pdfminer.six` 解析字符流的物理空间坐标 $(x, y)$，通过聚类算法重构段落与阅读顺序，避免左右双栏文本横向串行；
> 2. 利用 `pdfplumber` 探测表格的横竖线边界网格，将其抽取为二维数组，最后格式化为 Markdown 语法输出。

### Q3：如果遇到恶意用户上传包含病毒或超大攻击文件，系统如何保障安全？
> **参考答案**：
> 项目在设计之初就考虑了安全防线：
> 1. **防止 XML 炸弹（Billion Laughs）**：全面采用安全增强的 `defusedxml` 代替 Python 标准 XML 库；
> 2. **防止 SSRF 与路径穿越**：提供了受限流式接口 `convert_stream()`，业务层可以先在内存或沙箱中校验文件元数据，再注入引擎解析；
> 3. **最小特权运行**：无常驻后台守护进程，严格继承主进程的无特权沙箱执行。

### Q4：与商业级云端 OCR（如百度、阿里或 Azure Doc Intelligence）相比，MarkItDown 的优势在哪里？
> **参考答案**：
> 1. **成本与速度**：MarkItDown 纯本地运行，不产生任何 API 调用账单，单文档处理只需几十毫秒，而云端 OCR 单页需要 2~5 秒且按页付费；
> 2. **数据隐私合规**：企业涉密合同与内网文档无需上传至公网云端；
> 3. **可扩展性**：对于扫描件这类确实需要 OCR 的特殊格式，MarkItDown 留有插件接口，可按需挂载本地轻量 OCR 或云端大模型视觉能力，做到“轻重分离、按需调度”。
